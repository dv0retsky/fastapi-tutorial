# Практическое занятие №13: Внедрение зависимостей и расширенная маршрутизация

## Вспомогательные приложения и маршрутизаторы API


### Суб-приложения

Например у вас была первая версия вашего API, но потом вы его сильно поменяли. Но хотите сохранить поддержку предыдущего. В FastAPI это сделать очень просто.

Допустим у вас есть файл `api_v1.py` (или другое суб-приложение):

```python
from fastapi import FastAPI

# создаём суб-приложение
api_v1_app = FastAPI()

# определяем роут в суб-приложении
@api_v1_app.get("/sub/")
def read_sub():
    return {"message": "This is a sub-application route."}
```

Потом посмотрим на основной файл вашего FastAPI, допустим `main.py`:

```python
from fastapi import FastAPI
from api_v1 import api_v1_app

# создаём главное FastAPI приложение
app = FastAPI()

# монтируем суб-приложение в основное приложение 
app.mount("/v1", api_v1_app)

# создаём обычный роут в главном приложении
@app.get("/")
def root():
    return {"message": "Hello from main app"}
```

Каждое подобное субприложение FastAPI будет иметь свою документацию, работать независимо от других приложений и будет обрабатывать свои запросы, зависящие от пути. В данном случае у нас будет доступен основной роут <http://localhost:8000/> и роут суб-приложения <http://localhost:8000/v1/sub/>. Как видим, для доступа к роутам суб-приложений используется префикс (у нас /v1/).

## Маршрутизаторы API

Когда маршрутов становится слишком много, то ими становится неудобно управлять. Маршруты могут дублироваться или перекрывать друг друга.

FastAPI имеет собственную систему API-маршрутизации. API-роуты (APIRouters) можно рассматривать как мини-приложения FastAPI, которые являются зависимой **частью** более крупного приложения (без основного приложения они не могут существовать).

Давайте посмотрим как FastAPI может помочь.

Например есть 3 файла:

Файл 1 - `electronics.py`:

```python
from fastapi import APIRouter

electronicsroute = APIRouter()

@electronicsroute.get('/info')
def electronics():
    return {"detail": "This electronics info is from the electronics APIRouter",
            "name": "Electronics XYZ",
            "brand": "ABC Electronics"}
```

Файл 2 - `gadgets.py`:

```python
from fastapi import APIRouter

gadgetsroute = APIRouter()

@gadgetsroute.get('/info')
def gadgets():
    return {"detail": "This gadgets info is from the gadgets APIRouter",
            "name": "Cool Gadget",
            "manufacturer": "Gadget Co."}
```

Как видите, в обоих файлах есть маршрут `/info`.

Чтобы их было возможно обрабатывать, давайте соединим их в третьем `main.py` файле:

```python
from fastapi import FastAPI
from electronics import electronicsroute
from gadgets import gadgetsroute


app = FastAPI()
app.include_router(electronicsroute, prefix="/electronics")
app.include_router(gadgetsroute, prefix="/gadgets")

@app.get('/')
def index():
    return "Welcome to the Electronics Store"
```

Вы могли заметить, что мы создавали не инстанс приложения FastAPI, как в случае с суб-приложениями, а использовали класс `APIRouter`.

В файле `main.py` мы включили оба роутера и установили префикс для каждого.

Теперь есть возможность обратиться как к основным роутам главного приложения (<http://localhost:8000/>), так и к каждому из роутов `/info`, используя соответствующий префикс: <http://localhost:8000/electronics/info> и <http://localhost:8000/gadgets/info>.

Таким образом, может быть несколько API-роутов для обработки параметров, в зависимости от того, какой тип операции нужно выполнить **для разных групп** эндпоинтов.

## Понимание внедрения зависимостей в FastAPI

Внедрение зависимостей (Dependency Injection, DI) — это шаблон проектирования, который позволяет отделить создание и конфигурацию объектов от их использования. В FastAPI этот подход используется для автоматического управления внешними ресурсами и сервисами, такими как подключения к базе данных, проверки аутентификации, кэширование, логирование и многое другое. Это позволяет сделать код более модульным, удобным для тестирования и масштабируемым, а также способствует соблюдению принципа **DRY** (Don’t Repeat Yourself).

### Что такое внедрение зависимостей?

В традиционном программировании функция или класс могут создавать свои зависимости непосредственно внутри своего тела. Например, если функция использует базу данных, она может создавать подключение самостоятельно. Такой подход затрудняет модульное тестирование и повторное использование кода, так как каждая функция «знает» о способе создания или получения зависимости.

С помощью внедрения зависимостей зависимости передаются в функции извне, что позволяет:

- **Легко изменять реализацию:** Вы можете заменить одну реализацию зависимости другой (например, для тестирования — использовать мок вместо настоящего подключения к БД).
- **Повторно использовать код:** Одна и та же логика (например, подключение к базе данных или проверка аутентификации) может использоваться в нескольких местах без дублирования.
- **Улучшить читаемость и поддержку:** Разделив ответственность за создание и использование зависимостей, код становится чище и проще для понимания.

### Как FastAPI реализует DI через `Depends`

FastAPI использует специальный класс `Depends` для объявления зависимостей. Когда вы указываете зависимость в параметрах функции-обработчика маршрута, FastAPI автоматически:

1. Находит функцию или класс, переданный в `Depends`.
2. Вызывает её (а при необходимости — передаёт свои собственные зависимости).
3. Полученный результат передаёт в функцию-обработчик маршрута в виде аргумента.

Такой механизм позволяет строить сложные цепочки зависимостей. Например, функция аутентификации может сама использовать зависимость для извлечения учетных данных, а затем другая функция — зависимость для доступа к базе данных. Все это происходит автоматически, без необходимости явно создавать или передавать объекты.

### Примеры и области применения

Рассмотрим несколько сценариев, в которых внедрение зависимостей особенно полезно:

- **Аутентификация и авторизация:**

Вместо того чтобы прописывать код проверки токена или пароля в каждом маршруте, вы можете создать функцию зависимости, которая занимается проверкой учетных данных. Если проверка не пройдена, функция выбрасывает исключение, и основной обработчик маршрута даже не запускается.

- **Подключения к базе данных:**

Создание и управление подключениями к базе данных можно централизовать в одной зависимости. Это не только исключает дублирование кода, но и позволяет использовать один и тот же объект подключения в нескольких маршрутах, что может положительно сказаться на производительности.

- **Кэширование и логирование:**

Зависимости могут использоваться для внедрения кэширования результатов или ведения журнала действий. Например, зависимость может проверять, есть ли уже кэшированные данные для запроса, и возвращать их, минуя повторные вычисления.

### Как устроен и как работает класс `Depends`

Класс `Depends` в FastAPI служит специальным маркером, который сообщает фреймворку, что данный параметр должен быть получен через систему внедрения зависимостей. Это означает, что вместо передачи значения напрямую, FastAPI автоматически вызывает переданный объект (обычно функцию или класс с методом `__call__`) и использует его результат в качестве значения параметра.

### Механизм работы `Depends`

При обработке запроса FastAPI выполняет следующие шаги:

1. Обнаруживает параметр функции-обработчика, у которого значение по умолчанию задано через `Depends`.
2. Извлекает объект, переданный в `Depends` (например, функция или класс).
3. Рекурсивно разрешает все зависимости, указанные внутри этого объекта, если таковые имеются (то есть, если функция сама использует `Depends` в своих параметрах).
4. Вызывает этот объект (выполняет функцию или вызывает метод `__call__` класса) и получает возвращаемое значение.
5. Передаёт полученное значение в качестве аргумента функции-обработчика маршрута.

Одной из полезных особенностей `Depends` является параметр `use_cache` (по умолчанию `True`). Это означает, что если одна и та же зависимость используется несколько раз в рамках одного запроса, она будет вызвана только один раз, а её результат будет кэшироваться для последующих обращений в этом же запросе.

### Что можно передавать в `Depends`

В качестве аргумента для `Depends` можно передавать:

- **Функции** – Это наиболее распространённый случай. Такие функции могут быть синхронными или асинхронными и могут сами объявлять свои зависимости через `Depends`.

Пример:

```python
def get_current_user():
    # Логика для получения текущего пользователя
    return {"username": "johndoe"}

@app.get("/users/me")
def read_current_user(current_user: dict = Depends(get_current_user)):
    return current_user
```

- **Классы с методом `__call__`** – Если вам нужно использовать объект с состоянием или более сложную логику, можно передавать класс, реализующий метод `__call__`.

Пример:

```python
class Authenticator:
    def __init__(self, secret: str):
        self.secret = secret

    def __call__(self):
        # Логика аутентификации с использованием self.secret
        return {"authenticated": True}

authenticator = Authenticator(secret="mysecret")

@app.get("/secure-data")
def secure_data(auth: dict = Depends(authenticator)):
    return auth
```

### Что не стоит передавать в `Depends`

Некоторые объекты и подходы не подходят для использования с `Depends`:

- **Не вызывайте функцию напрямую** – Не передавайте результат вызова функции, например `Depends(get_current_user())`. Всегда передавайте сам объект функции, чтобы FastAPI мог самостоятельно управлять моментом её вызова.
- **Невызываемые объекты** – Передавайте только те объекты, которые являются `callable` (то есть функциями или классами с методом `__call__`). Передача обычных значений (например, строки или чисел) не имеет смысла, так как они не могут быть вызваны для разрешения зависимости.
- **Слишком сложные конструкции в лямбдах** – Хотя можно использовать lambda-функции, рекомендуется избегать сложных лямбда-выражений, так как они ухудшают читаемость кода и затрудняют отладку.

### Подробное описание работы `Depends`

Когда вы объявляете зависимость через `Depends`, вы передаете функцию или класс, который FastAPI должен вызвать. Рассмотрим следующий пример:

```python
def get_database():
    # Здесь может быть логика подключения к реальной базе данных
    database_connection = {"connection": "fake_db_connection"}
    return database_connection

@app.get("/items/")
def read_items(database = Depends(get_database)):
    return {"items": ["item1", "item2"], "db_connection": database}
```

В этом примере функция `get_database` вызывается автоматически перед выполнением функции `read_items`. Результат вызова (в данном случае симуляция подключения к базе данных) передаётся в параметр `database`. Если в дальнейшем потребуется изменить способ получения подключения, достаточно изменить только функцию `get_database`, а все маршруты, использующие эту зависимость, автоматически получат обновлённую реализацию.

### Управление жизненным циклом зависимостей

Одним из важных аспектов DI является управление временем жизни зависимостей. FastAPI позволяет задавать область применения зависимостей, например:

- **На уровне запроса:**

Зависимость создается заново для каждого запроса. Это полезно для объектов, состояние которых не должно сохраняться между запросами.

- **На уровне приложения:**

Зависимость может быть создана один раз и использоваться во всех запросах. Это особенно удобно для дорогостоящих операций, таких как подключение к базе данных или настройка внешних сервисов.

Такой подход позволяет оптимизировать производительность и правильно управлять ресурсами.

### Преимущества и недостатки использования DI в FastAPI

**Преимущества:**

- Повышенная модульность и читаемость кода.
- Упрощение тестирования за счёт возможности замены зависимостей на моки или фиктивные реализации.
- Соблюдение принципа DRY, так как общий код выносится в отдельные функции или классы.
- Гибкость в управлении внешними ресурсами, такими как базы данных, сервисы аутентификации и т.д.

**Недостатки:**

- Начальная сложность понимания механизма DI, особенно для начинающих разработчиков.
- Могут возникать сложности с отладкой, так как цепочки зависимостей могут быть довольно длинными.
- При неправильной организации зависимостей возможны проблемы с производительностью и управлением ресурсами, если не учитывать область их применения.

### Промежуточное резюме

Внедрение зависимостей в FastAPI — это не просто механизм для уменьшения повторяемости кода. Это фундаментальный подход, который помогает строить масштабируемые, модульные и легко тестируемые приложения. Использование Depends позволяет сосредоточиться на логике приложения, не отвлекаясь на детали создания и управления зависимостями. С практикой и изучением примеров вы научитесь эффективно применять DI для решения самых разнообразных задач, будь то обеспечение безопасности, работа с базами данных или интеграция с внешними сервисами.

В дальнейшем мы рассмотрим более сложные примеры и альтернативы встроенной системе внедрения зависимостей, что поможет вам выбрать оптимальный подход для вашего проекта.

## Зависимости маршрутов и области их применения

FastAPI позволяет определять зависимости для конкретного маршрута с помощью класса `Depends`. Это даёт возможность не только повторно использовать код (соблюдая принцип DRY — Don’t Repeat Yourself), но и управлять временем жизни объектов, которые внедряются в обработчики запросов. В зависимости от того, как вы определяете функцию зависимости, её экземпляр может создаваться заново для каждого запроса или использоваться повторно на уровне всего приложения.

Стоит отметить, что зависимости в FastAPI могут быть созданы и использоваться на разных уровнях.

### Объявление зависимостей в эндпоинте

Вы можете объявить зависимости непосредственно в функции-обработчике маршрута. Это означает, что для данного эндпоинта FastAPI автоматически вызовет указанную функцию зависимости и передаст её результат в качестве аргумента. Например:

```python
from fastapi import FastAPI, Depends

app = FastAPI()

def get_current_user():
    # Логика для получения текущего пользователя
    return {"username": "johndoe"}

@app.get("/users/me")
def read_current_user(current_user: dict = Depends(get_current_user)):
    return current_user
```

В этом примере функция `get_current_user` вызывается при обращении к маршруту `/users/me`, и её результат передается в параметр `current_user`.

### Объявление зависимостей в роутере

FastAPI позволяет группировать маршруты в `APIRouter` и задавать зависимости для всего роутера. Это удобно, когда все маршруты в группе требуют общих проверок или доступа к одним и тем же ресурсам (например, аутентификация или подключение к базе данных). Пример:

```python
from fastapi import APIRouter, Depends

router = APIRouter(
    prefix="/items",
    dependencies=[Depends(get_current_user)]  # Все маршруты этого роутера используют get_current_user
)

@router.get("/")
def read_items():
    # get_current_user уже выполнен для каждого запроса
    return [{"item_id": "Foo"}, {"item_id": "Bar"}]

# Подключение роутера к приложению
app.include_router(router)
```

Здесь зависимость `get_current_user` будет автоматически применяться ко всем маршрутам, зарегистрированным в роутере.

> [!WARNING]
> Обратите внимание, что значения из зависимостей группы роутов (роутера) и глобальные зависимости (для всего приложения) НЕ передают значения в функцию-обработчик маршрута! То есть они удобны для какой-то логики, не требующей передачи внутрь функции (например проверка токена), и скорее всего либо будут выполнены успешно, либо выбросят исключение.

### Объявление зависимостей на уровне приложения

Для глобальных зависимостей, которые должны применяться ко всем маршрутам приложения, можно указать их при создании экземпляра `FastAPI`. Это особенно полезно для таких задач, как логирование, глобальная аутентификация или настройка общих ресурсов:

```python
from fastapi import FastAPI, Depends

def global_dependency():
    # Логика, применяемая ко всем запросам
    return "global data"  # де-факто нет смысла что-то возвращать, т.к. значение не передастся в обработчик маршрута. 
    # тут скорее будет зависимость по получению общих для всей аппы заголовков или что-то такое
    # например провалидировали версию фронта, если ниже необходимой - вход заблокировали, вызвав ошибку (вынуждаем обновляться)

app = FastAPI(dependencies=[Depends(global_dependency)])

@app.get("/global")
def read_global():
    return {"message": "Эта функция использует глобальную зависимость"}
```

В этом примере функция `global_dependency` вызывается для каждого запроса независимо от маршрута.

### Пример с поддельной базой данных

Рассмотрим теоретический пример, где у нас есть поддельная база данных, содержащая информацию о пользователях. Мы создаём зависимость для получения экземпляра этой базы, которую затем внедряем в функции маршрутов.

```python
from fastapi import FastAPI, Depends

app = FastAPI()

# Фейковая база данных для хранения пользовательской информации
fake_database = {
    1: {"id": 1, "name": "John Doe"},
    2: {"id": 2, "name": "Jane Smith"},
}

# Функция зависимости для получения экземпляра базы данных
def get_database():
    return fake_database

# Маршрут для получения данных конкретного пользователя
@app.get("/users/{user_id}")
def get_user(user_id: int, database: dict = Depends(get_database)):
    if user_id in database:
        return database[user_id]
    else:
        return {"message": "User not found"}

# Маршрут для получения всех пользователей
@app.get("/users/")
def get_all_users(database: dict = Depends(get_database)):
    return list(database.values())
```

В этом примере мы определяем поддельную базу данных `fake_database` для хранения пользовательской информации. Мы также создаем функцию зависимости `get_database`, которая возвращает экземпляр базы данных (`fake_database`).

В обеих функциях маршрутизации `get_user` и `get_all_users` мы используем `Depends(get_database)`, чтобы внедрить `fake_database` в функции в качестве зависимости. Функция `Depends` сообщает FastAPI вызвать `get_database()` и передать возвращаемое значение в качестве аргумента функции каждого роута.

Когда мы отправляем запрос GET в `/users/{user_id}` или `/users/`, FastAPI автоматически вводит (добавляет) `fake_database` в соответствующие функции маршрута, позволяя нам получить доступ к пользовательской информации из базы данных в наших обработчиках. И в дополнение - мы соблюли принцип DRY - don't repeat yourself, переиспользовав свою зависимость, что сделало код более читаемым и удобным.

### Время жизни экземпляров

Зависимости на уровне запроса

При использовании зависимости по умолчанию функция зависимости вызывается для каждого входящего запроса. Это означает, что объекты, созданные в рамках зависимости, не сохраняют своё состояние между запросами. Например, генерация уникального идентификатора для каждого запроса:

```python
import uuid
from fastapi import FastAPI, Depends

app = FastAPI()

def get_request_id():
    # Каждый запрос получает уникальный идентификатор
    return str(uuid.uuid4())

@app.get("/request/")
def read_request(request_id: str = Depends(get_request_id)):
    return {"request_id": request_id}
```

В этом случае каждый новый запрос вызывает функцию `get_request_id()`, генерируя для него новый уникальный идентификатор.

**Кэширование зависимостей**

Если необходимо, чтобы зависимость создавалась один раз и использовалась во всех запросах, можно воспользоваться механизмом кэширования. Один из способов — использовать декоратор `@lru_cache` из модуля `functools`, который сохраняет результат вызова функции:

```python
from functools import lru_cache
from fastapi import FastAPI, Depends

app = FastAPI()

@lru_cache()
def get_config():
    # Эта функция вызывается один раз, затем результат кэшируется
    return {"db_url": "sqlite:///:memory:", "debug": True}

@app.get("/config/")
def read_config(config: dict = Depends(get_config)):
    return config
```

В этом примере функция `get_config()` вызывается только один раз, а её результат используется для всех последующих запросов, что особенно полезно для конфигурационных данных или подключения к базе данных.

### Переопределение зависимостей (`dependency_overrides`)

FastAPI предоставляет механизм переопределения зависимостей, который особенно полезен для тестирования или изменения поведения приложения в различных средах. С помощью словаря `app.dependency_overrides` можно заменить оригинальную зависимость альтернативной реализацией:

```python
def override_get_database():
    # Переопределённая зависимость для тестирования
    return {
        1: {"id": 1, "name": "Test User"}
    }

# Переопределяем оригинальную зависимость
app.dependency_overrides[get_database] = override_get_database
```

Теперь все маршруты, использующие Depends(`get_database`), будут получать данные из `override_get_database()`.

### Недостатки встроенной системы `Depends` и альтернативы

Несмотря на удобство и простоту использования, встроенная система зависимостей FastAPI имеет ряд ограничений:

- **Ограниченная функциональность для сложных случаев:**

При большом количестве вложенных зависимостей цепочки вызовов могут становиться сложными для отладки. В таких случаях встроенные возможности Depends могут оказаться недостаточными для эффективного управления зависимостями.

- **Управление временем жизни объектов:**

Хотя для простых случаев можно использовать кэширование через @lru_cache, для более сложных сценариев может потребоваться специализированный DI-контейнер, который обеспечит гибкое управление временем жизни и состоянием объектов.

- **Альтернативные инструменты:**

В реальной работе часто применяются более эффективные инструменты внедрения зависимостей, такие как **Dishka** или **Punq** (в зависимости от предпочтений команды и специфики проекта). Эти инструменты предоставляют расширенные возможности по автоматическому разрешению зависимостей, более тонкому управлению временем жизни объектов и улучшенной интеграции с другими компонентами приложения.

### Заключение

Использование зависимостей в FastAPI посредством `Depends` позволяет создавать чистый, модульный и легко тестируемый код. Вы можете задавать зависимости как на уровне каждого запроса, так и на уровне всего приложения, используя механизмы кэширования для оптимизации производительности. Механизм переопределения зависимостей (`dependency_overrides`) дополнительно упрощает тестирование и адаптацию приложения в различных средах.

Более подробно про зависимости [**тут**](https://fastapi.tiangolo.com/tutorial/dependencies/).

Скорее всего, в реальной работе вы будете использовать более эффективный инструмент внедрения зависимостей (например, Dishka или Punq), поэтому можете прочитать [**тут**](https://habr.com/ru/articles/867040/) более подробно про DI, недостатки `Depends` и альтернативы.

## Middleware и CORS

Мидлвэр в FastAPI - это такая прослойка для каждого запроса (ответа). Другими словами это функция, которая работает с каждым запросом до того, как он будет обработан какой-либо конкретной операцией path. А также с каждым ответом, прежде чем возвращать его.

Порядок работы Middleware'а такой:

1. Он принимает каждый запрос , который приходит к вашему приложению.
2. Затем он может что-то сделать с этим запросом или запустить любой необходимый код.
3. Затем он передает запрос на обработку остальной части приложения (некоторой `Path` операции).
4. Затем он принимает ответ, сгенерированный приложением (некоторой операцией пути).
5. Он может что-то сделать с этим ответом или запустить любой необходимый код.
6. Затем он возвращает ответ .

Примеров применения может быть множество. Вот некоторые из них: блэк лист для айпи-адресов, вайт-лист, введение "паузы" для загрузки, проверка "доверенных" заголовков, редирект (например на https/wss) и др.

Например, можно сделать мидлвэр, который делает вид, что сервер долго грузится при частых обращениях с одного и того же айпишника. Пожалуй главная цель такого ПО - снижение нагрузки на сервер. Либо на этом "промежуточном" слое можно делать что-то, что является общим для всех запросов (например, проверка или добавление заголовков), чтобы не прописывать такую логику в каждой функции. 

**Middleware** создаётся в FastAPI довольно просто - с использованием декоратора `@app.middleware("http")`.

Вот пример Мидлвэра, который вы можете запустить у себя и увидеть логику его работы:

```python
from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def my_middleware(request: Request, call_next):
    print('Мидлвэр начал работу')
    response = await call_next(request)
    print('Мидлвэр получил обратно управление')
    return response

@app.get("/")
def index():
    print('привет из основного обработчика пути')
    return {"message": "Hello, world!"}
```

Давайте для примера разберём пример из официальной документации:

```python
import time

from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def add_process_time_header(request: Request, call_next):
    start_time = time.time()
    response = await call_next(request)
    process_time = time.time() - start_time
    response.headers["X-Process-Time"] = str(process_time)
    return response
```

Мы создали Мидлвэр с помощью декоратора. 

Потом определили логику его работы (в качестве аргументов указали функцию, которая принимает сам объект запроса `Request` и функцию `call_next`).

`Call_next` - это функция, которая передает управление дальше соответствующему обработчику пути (обработчик в примере не указан, но предполагается, что есть какой-то).

Потом засекли текущее время. Сказали, что ответом будет то, что вернёт функция call_next (соответствующий обработчик пути). И сказали, что время обработки - это разница между временем текущим и тем, когда мы передали управление в другой обработчик.

И потом мы добавляем к каждому ответу **кастомный заголовок** - время обработки запроса.

### CORS (Cross-Origin Resource Sharing)

**CORS** — это механизм, который позволяет ограничивать доступ к ресурсам веб-страниц в браузере из других источников (например, с другого домена). Это важно, чтобы защитить сервер от непроверенных запросов с других доменов.

Веб-браузеры по умолчанию блокируют такие запросы, чтобы предотвратить атаки типа **Cross-Site Request Forgery (CSRF)** и другие проблемы безопасности. CORS разрешает серверам явно указывать, какие источники (домен/сайт) могут обращаться к их ресурсам.

### Пример использования CORS Middleware в FastAPI

FastAPI имеет встроенную поддержку CORS, и вы можете легко добавить его с помощью мидлвэра. Для этого используется специальная библиотека `fastapi.middleware.cors.CORSMiddleware`. Вот пример:

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

# Настроим CORS
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],  # Разрешаем запросы с любых доменов
    allow_credentials=True,
    allow_methods=["*"],  # Разрешаем все HTTP-методы
    allow_headers=["*"],  # Разрешаем все заголовки
)

@app.get("/")
async def index():
    return {"message": "CORS работает!"}
```

Здесь:

- `allow_origins=["*"]` — разрешает доступ с любого домена.
- `allow_methods=["*"]` — разрешает все HTTP-методы (GET, POST, PUT и т.д.).
- `allow_headers=["*"]` — разрешает любые заголовки.

Если вы хотите ограничить доступ только для определенных доменов, например, для <https://example.com>, просто замените `"*"` на список нужных доменов:

```bash
allow_origins=["https://example.com"]
```

> [!WARNING]
> *Примечание: по соображениям безопасности в продакшене не рекомендуется использование подхода с разрешением всего через "*". Вместо этого следует перечислить все источники (возможные домены/субдомены, где будет находиться ваш фронтенд), все разрешенные заголовки, а также все разрешенные методы.*

В общем CORS — это полезный инструмент для работы с запросами из разных источников.

## Усовершенствованные методы маршрутизации

FastAPI предоставляет различные расширенные методы маршрутизации для настройки поведения конечной точки и обработки сложных шаблонов запросов.

- Настройка путей маршрута: Вы можете **настроить пути маршрута**, используя переменные, регулярные выражения и параметры запроса, для создания динамических и гибких конечных точек.
- Обработка HTTP-методов: FastAPI позволяет вам определять **несколько HTTP-методов** (`GET`, `POST`, `PUT`, `DELETE` и т.д.) **для одного маршрута**, что позволяет создавать более универсальные API.
- Включение и исключение маршрутов: Вы можете выборочно включать или не **включать маршруты в приложение**, используя include. Это позволяет лучше контролировать открытые конечные точки API.

## Вложенные объекты для тела запроса

FastAPI предоставляет более широкие возможности при проверке данных запроса при помощи Pydantic моделей.

Рассмотрим пример:

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Image(BaseModel):
    url: str
    name: str


class Item(BaseModel):
    name: str
    description: str | None = None
    price: float
    tax: float | None = None
    tags: list[str] = []
    image: Image | None = None


@app.put("/items/{item_id}")
async def update_item(item_id: int, item: Item):
    results = {"item_id": item_id, "item": item}
    return results
```

Тут мы сначала объявили модель `Image`, и далее в объекте `Item` её вложили. После этого передали эту модель в соответствующую функцию, обрабатывающую PUT-запрос. Соответственно FastAPI будет ожидать такой входящий JSON:

```json
{
    "name": "Foo",
    "description": "The pretender",
    "price": 42.0,
    "tax": 3.2,
    "tags": ["rock", "metal", "bar"],
    "image": {
        "url": "http://example.com/baz.jpg",
        "name": "The Foo live"
    }
}
```

Таким образом FastAPI позволяет настраивать валидируемые схемы данных любым удобным для нас способом, что повышает общую гибкость приложения.

Напомним, что FastAPI автоматически генерирует UI-документацию для вашего кода благодаря поддержке Swagger (через него также можно делать тестирование вашего API). Её можно посмотреть по адресам:
